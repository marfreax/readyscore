# PHASE 3.0-D.1-F.10-B.6 — RIASEC Question Bank Lifecycle Reconciliation

## Critical finding from actual v2 source

The current ReadyScore source contains TWO Question Bank lifecycle representations:

### Admin Question Bank

```text
lib/question-bank-admin.ts
        ↓
data/question-bank/admin-question-bank.json
```

The existing admin actions operate on this file-backed state:

```text
mapping-approve
approve
publish
unpublish
```

The source confirms:

```text
approveMapping()
approveQuestion()
publishQuestion()
```

and the admin UI calls:

```text
/api/admin/question-bank/[questionId]/mapping-approve
/api/admin/question-bank/[questionId]/approve
/api/admin/question-bank/[questionId]/publish
```

### Runtime Question Bank

The assessment runtime uses the PostgreSQL-backed Question / QuestionVersion repository:

```text
lib/question-bank-repository.ts
        ↓
PostgreSQL
        ↓
getPublishedEligibleQuestions()
```

The RIASEC 84 candidates were imported into PostgreSQL by F.10-B.2.

## Architectural consequence

We MUST NOT execute F.10-B.6 as a simple "approve 60 questions" operation yet.

If approval is performed only through the existing admin UI/routes, it can change:

```text
admin-question-bank.json
```

without changing the PostgreSQL QuestionVersion lifecycle used by runtime.

That would create:

```text
ADMIN STATE          POSTGRESQL RUNTIME
    APPROVED   ≠          DRAFT
```

This is a source-of-truth split.

Therefore F.10-B.6 is a reconciliation gate, not an approval mutation.

---

# 1. Required Target Architecture

For RIASEC production:

```text
Review Artifact
      ↓
Approval Decision
      ↓
Canonical Question Bank
      ↓
PostgreSQL QuestionVersion
      ↓
APPROVED
      ↓
PUBLISHED
      ↓
getPublishedEligibleQuestions()
      ↓
RIASEC runtime
```

The admin file-backed state must either:

1. be retired from the production lifecycle, or
2. be explicitly synchronized with PostgreSQL.

We do NOT silently choose either option in this phase.

# 3. No Database Mutation

F.10-B.6 must not:

```text

publish
unpublish
delete
rewrite
```

any RIASEC question.

This phase exists to prevent an approval action from modifying the wrong source of truth.

---

# 4. Canonical Source Decision

Before F.10-B.7, the project must explicitly select:

```text
CANONICAL_QUESTION_BANK = POSTGRESQL
```

for the runtime.

Reason:

The current assessment runtime already queries the PostgreSQL repository for
published eligible questions.

Therefore PostgreSQL must be the authoritative production lifecycle source
for the RIASEC runtime.

The file-backed admin state may remain as a legacy/admin compatibility layer,
but it cannot independently define production eligibility.

# 6. Approval Lifecycle

RIASEC item lifecycle:

```text
DRAFT
  │
  ├── mapping review
  ↓
MAPPED
  │
  ├── mapping approval
  ↓
MAPPING APPROVED
  │
  ├── content approval
  ↓
APPROVED
  │
  └── publication
       ↓
PUBLISHED
```

Runtime eligibility:

```text
PUBLISHED + APPROVED mapping
```

only.

# Important

Do NOT use the existing `/admin/question-bank` Approve/Publish buttons
for RIASEC production until the admin-to-PostgreSQL lifecycle reconciliation
is implemented.

The existing source shows that those admin functions operate on
`admin-question-bank.json`, while the runtime uses the PostgreSQL repository.
This is precisely the type of split that can produce a false "published"
question that runtime cannot actually see.
