# ReadyScore V14.3 — Fulfillment, Entitlement & Customer Access

## Status
DEVELOPMENT — implementation artifact; not yet PASS/FROZEN.

## Objective
Connect verified paid transactions to deterministic, idempotent fulfillment, concrete customer entitlements, and an assessment access boundary without changing V13 measurement/scoring contracts.

## Implemented
- `CommercialFulfillment` durable one-per-order fulfillment ledger.
- Paid-order fulfillment boundary with retryable `FULFILLMENT_FAILED` state.
- Product-to-entitlement mapping from the persisted product definition.
- BASIC mapping requires a concrete `assessmentTypeSnapshot`; no arbitrary/default test is selected.
- Entitlement provenance through `sourceOrderId`.
- Entitlement usage ledger through `usageLimit` / `usageConsumed`.
- Automatic fulfillment after verified `PAID` payment from V14.2 verification/webhook paths.
- Customer delivery status and safe fulfillment retry endpoint.
- Assessment start access boundary for the four production paid tests.
- Atomic compare-and-set access consumption inside the same transaction that creates the assessment attempt.
- Access denial when no active consumable entitlement remains.
- Audit events for fulfillment and access consumption where an order provenance exists.
- V14.3 static gate and real HTTP E2E fixture.

## Important compatibility rule
V13 assessment selection, timer, answer persistence, submit, timeout, scoring, and result semantics remain unchanged. V14.3 only establishes whether a customer may start a paid core assessment and consumes the commercial access atomically with attempt creation.

## BASIC selection constraint
The frozen V14.1 checkout implementation does not currently persist a selected core test for `product-basic`; its `assessmentTypeSnapshot` can therefore be null. V14.3 intentionally fails fulfillment with `FULFILLMENT_CONFIGURATION_MISSING` rather than guessing a test. Medium/Advance have deterministic product entitlement definitions and are the canonical V14.3 E2E products. A future checkout amendment is required if BASIC is to become a fully automatic purchase-to-access path.

## FIX1 — Typecheck Corrections

Applied after real environment validation exposed compile-time issues:
- restored `applyVerifiedStatus()` transaction result binding before fulfillment handling;
- mapped commercial `COGNITIVE` identity to the existing single-test `IQ` commercial identity before entitlement definition generation;
- allowed readonly entitlement definition collections in validation.

No schema, migration, payment provider, or assessment-runtime contract change.


## FIX3 — E2E Fixture Isolation

Applied after real HTTP/PostgreSQL validation showed that the configured E2E account already owned aggregated `TEST_ACCESS` entitlements from an earlier order. The production fulfillment implementation correctly aggregates repeated purchases into existing user entitlements by incrementing `usageLimit`; therefore assertions requiring `sourceOrderId === current order` were invalid for a reused customer.

FIX3 changes only the V14.3 E2E fixture:
- creates a fresh customer through the real `POST /api/auth/register` HTTP endpoint on every run;
- uses a unique Yopmail address generated at runtime;
- uses the existing `READYSCORE_AUTH_E2E_PASSWORD` environment value;
- uses the session returned by registration;
- leaves production fulfillment, entitlement aggregation, assessment access, schema, and migrations unchanged;
- preserves the existing entitlement, duplicate-fulfillment, atomic-consumption, and concurrent-access assertions because the fresh customer starts without prior paid entitlements.

FIX3 is an E2E fixture-isolation correction, not a fulfillment implementation fix.

## FIX4 — Concurrent Access Error Contract Mapping

**Scope:** narrow HTTP error-contract fix only.

The V14.3 E2E proved that entitlement consumption remained atomic under two concurrent assessment-start requests: exactly one request succeeded, while the losing request surfaced the repository CAS sentinel `ASSESSMENT_ACCESS_RACE` as an unhandled error and therefore returned HTTP 500.

FIX4 does not change the compare-and-set transaction, entitlement counters, assessment selection, scoring, timer, or fulfillment behavior. It only maps `ASSESSMENT_ACCESS_RACE` at the assessment runtime boundary to the existing public access-denied contract: `RuntimeError("TEST_ACCESS_REQUIRED", ...)`, which the existing route exposes as HTTP 422.

**Expected concurrent contract after FIX4:**
- exactly one request → HTTP 200 / assessment attempt created
- exactly one losing request → HTTP 422 / `TEST_ACCESS_REQUIRED`
- no second entitlement consumption

**Production source changed:** `lib/assessment/runtime-service.ts` only.
