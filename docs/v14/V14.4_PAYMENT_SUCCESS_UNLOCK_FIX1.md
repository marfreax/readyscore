# V14.4 — Payment Success & Customer Unlock FIX1

## Problem confirmed

A real Midtrans Sandbox BCA Virtual Account transaction reached `settlement`, but the customer was redirected to Midtrans's default `example.com` finish URL and the ReadyScore account remained locked.

The previous implementation relied on the Midtrans HTTP Notification path to move the order to `PAID` and trigger V14.3 fulfillment. The customer-facing success page did not reconcile the order when the notification had not yet reached ReadyScore.

## Fix

1. Midtrans Snap token creation now sends a customer-specific `callbacks.finish` and `callbacks.error` URL to `/checkout/success` using `READYSCORE_PUBLIC_URL`.
2. `/checkout/success` reads Midtrans's `order_id` query parameter and performs server-side status verification through the existing Midtrans Get Status boundary.
3. A paid order whose fulfillment is not yet complete is retried through the existing V14.3 idempotent fulfillment boundary.
4. The success page explicitly shows `PAID`, fulfillment/access readiness, and a direct route to Access & Plans or the purchased assessment.
5. Pending/failed/expired/cancelled payment states remain distinct; the redirect query is never trusted as the authoritative payment state.
6. V14.4 E2E now verifies the payment success landing page after settlement and confirms that access is unlocked.

## Required staging configuration

Set:

`READYSCORE_PUBLIC_URL=https://<staging-domain>`

The application refuses to create a production/staging payment when this value is missing rather than silently falling back to localhost.

Midtrans Dashboard must also have the ReadyScore webhook endpoint configured as the Payment Notification URL:

`https://<staging-domain>/api/commercial/webhooks/midtrans`

The webhook remains the asynchronous source of truth; the customer return path additionally performs server-side Get Status so a customer is not left locked when the notification arrives later.

## Security invariant

The implementation does not trust `transaction_status=settlement` from the browser redirect. It verifies the order ownership, provider reference, amount, currency, and current provider status server-side before marking the order paid and fulfilling entitlement.

## No migration

No database migration is introduced. The fix uses the existing V14.1-V14.3 commercial order, payment, webhook, fulfillment, and entitlement schema.
