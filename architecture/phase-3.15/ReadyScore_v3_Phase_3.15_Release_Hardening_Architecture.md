## 1. Scope

Phase 3.15 is the final engineering hardening layer before a release candidate is treated as release-ready.

It does not introduce a new measurement model, assessment instrument, scoring rule, recommendation rule, commercial entitlement rule, or institutional access rule.

## 3. Release Hardening Contract

V1 validates the release candidate structurally across:

```text
SOURCE INTEGRITY
    ↓
ARCHITECTURE / CONTRACT PRESENCE
    ↓
ROUTE SURFACE
    ↓
DATABASE / MIGRATION CONTRACT
    ↓
VERSIONING CONTRACT
    ↓
FROZEN RIASEC REGRESSION PRESENCE
    ↓
CALIBRATION GOVERNANCE PRESENCE
    ↓
COMMERCIAL / INSTITUTION BOUNDARY PRESENCE
    ↓
PACKAGE / RELEASE HYGIENE
```

This gate is a hardening gate. It does not replace:

```text
pnpm typecheck
pnpm build
pnpm db:migrate:deploy
pnpm e2e:riasec
```

and it does not claim those commands have passed merely because the static hardening gate passes.

## 4. Source Integrity

A release candidate must not contain:

```text
.env
.env.*
node_modules/
.next/
*.log
```

The source archive must also not depend on macOS metadata such as:

```text
__MACOSX/
.DS_Store
```

These are release-package hygiene rules, not application runtime rules.

` .DS_Store ` may be generated by macOS Finder after extraction into a working
tree. The canonical gate therefore ignores this non-source workspace metadata
while the release ZIP generator must continue to exclude it from the archive.

## 6. Database Contract

V1 requires:

```text
prisma/schema.prisma
prisma/migrations/
pnpm-lock.yaml
```

Migration folders must have unique names and deterministic ordering.

Phase 3.14 introduced no Prisma migration. Release hardening must not create calibration persistence as a side effect.

Phase 3.15 itself does not require a Prisma migration.

## 7. Versioning Contract

The release candidate must preserve versioned measurement identity, including the ability to trace:

```text
Question Bank Version
QuestionVersion
Taxonomy Version
Assessment Configuration Version
Selection Algorithm Version
Scoring Version
Result Contract Version
```

For the current frozen RIASEC runtime, the release candidate must retain:

```text
RIASEC_RESULT_V1
RIASEC_SCORE_V1
```

The gate does not replace or rewrite these versions.

## 8. Frozen RIASEC Regression

The release candidate must retain an executable `pnpm e2e:riasec` script and its production assertions for:

```text
60 selected questions
10 / 10 / 10 / 10 / 10 / 10
60 answer submissions
persistence / reload
submit + scoring
RIASEC_RESULT_V1
six dimensions
topCode
scoring version
```

The Phase 3.15 gate does not execute the E2E itself. It verifies that the regression protection remains wired into the release candidate.

## 9. Calibration Governance

The release candidate must retain:

```text
MEASUREMENT_CALIBRATION_V1
CALIBRATION_REPORT_V1
```

and the explicit safety boundary:

```text
productionMutation = false
scoringMutation = false
questionPublicationMutation = false
normingPerformed = false
validityClaim = false
```

No calibration result may automatically rewrite production measurement.

## 10. Commercial / B2B Boundary

Release hardening must preserve the architectural separation:

```text
PRODUCT
PRODUCT TIER
ENTITLEMENT
        ≠
TEST TYPE
ASSESSMENT CONFIGURATION
```

and:

```text
USER
  ↓
INSTITUTION MEMBERSHIP
  ↓
INSTITUTION ENTITLEMENT
```

Institutional access must remain resource-based and must not be implemented as product-tier coupling.

## 11. Measurement / Recommendation Boundary

The release candidate must preserve:

```text
MEASUREMENT
    ↓
PROFILE
    ↓
DIRECTION
    ↓
FIT
    ↓
EXPLORATION
```

No release-hardening change may introduce:

```text
ONE TEST
   ↓
MAJOR

ONE TEST
   ↓
CAREER
```

as a deterministic rule.

## 12. Mutation Safety

Phase 3.15 itself is read-only.

The hardening gate must not:

```text
approve questions
publish questions
rewrite QuestionVersion
change scoring versions
rewrite production results
grant commercial entitlements
create institution memberships
modify assessment attempts
```

The gate is a release inspection, not a migration or lifecycle mutation command.

## 13. Explicitly Deferred

Release hardening does not imply implementation of:

```text
Payment
Checkout
Subscription billing
Payment gateway
Invoice
Purchase webhook
Refund
Renewal / cancellation automation
Psychometric validation certification
Norming
IRT calibration
Automated question replacement
Automated production scoring recalibration
```

A release-ready engineering baseline is not equivalent to psychometric validation.

## 15. Release Verification Sequence

The canonical release candidate verification remains:

```bash
rm -rf .next

pnpm typecheck
pnpm build
pnpm release:hardening:gate
pnpm commercial:gate
pnpm e2e:riasec
```

If database state is being promoted to a new environment, run:

```bash
pnpm db:migrate:deploy
```

before the runtime regression.

The hardening gate does not substitute for database migration deployment.

## 17. Architectural Decision

Phase 3.15 is intentionally narrow:

```text
HARDEN
≠
REDESIGN
```

It exists to make the existing frozen architecture safer to release, not to reopen measurement, recommendation, commercial, institution, or assessment semantics.

After Phase 3.15 passes, the next work requires an explicit new roadmap decision rather than silently extending Phase 3.15.
