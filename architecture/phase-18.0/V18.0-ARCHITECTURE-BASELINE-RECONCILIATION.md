# ReadyScore V18.0 — Architecture & Baseline Reconciliation

**Status:** Architecture Baseline / Implementation Scope Locked  
**Baseline:** V17.11 — Question Architecture Freeze & Full Regression — PASS  
**Phase:** V18.0  
**Production mutation:** NONE

## 1. Purpose

V18.0 does not implement new WhatsApp runtime behavior. It reconciles the last V17.11 PASS source baseline against the V18 WhatsApp Production Runtime Completion specification and locks the exact implementation boundary for V18.1–V18.3.

The existing V17 WhatsApp implementation is preserved. V18.0 classifies what already exists, what is incomplete, and where each remaining gap belongs.

## 2. Baseline Findings

The V17.11 source baseline already contains a substantial WhatsApp operational layer:

- Meta webhook GET verification.
- POST webhook signature validation.
- Webhook payload normalization.
- WhatsApp conversation/message persistence.
- Phone normalization and channel-aware conversation uniqueness.
- Provider message idempotency through `externalMessageId`.
- Delivery/read/failed status persistence.
- Admin WhatsApp inbox at `/admin/whatsapp`.
- Authenticated admin API boundary.
- Conversation pagination and search.
- Message pagination.
- Admin text reply through Meta Graph API.
- Provider error mapping.
- Admin send rate limiting.
- BusinessLead exact matching and explicit linking.
- Assessment / Free Report customer context.
- Audit events for send/read/link operations.
- Existing V17 WhatsApp static gates and local E2E scripts.

These capabilities are **baseline assets**, not candidates for rewrite.

## 3. Architecture Reconciliation

### 3.1 Provider boundary

**Locked:** Meta WhatsApp Cloud API remains the only WhatsApp provider boundary.

The existing `lib/whatsapp/cloud-api-client.ts` is the provider integration point. No second provider client is required.

### 3.2 Conversation boundary

**Locked:** `WhatsAppConversation` and `WhatsAppMessage` remain the operational conversation layer.

No second customer/CRM identity model is introduced.

### 3.3 Customer identity

**Locked:** normalized WhatsApp phone number + `WHATSAPP` channel is the deterministic conversation identity.

`BusinessLead` remains the existing ReadyScore identity/context system. Matching by name alone is not allowed.

### 3.4 Assessment boundary

**Locked:** WhatsApp consumes existing assessment/result/report context only.

The V18 work must not modify the V17.11 Question Architecture, scoring, result, report, or historical attempt snapshot architecture.

### 3.5 Admin boundary

**Locked:** existing ReadyScore authentication and admin authorization remain the authorization system.

No WhatsApp-specific authentication or RBAC system is introduced.

### 3.6 API boundary

**Locked:** existing ReadyScore API response conventions remain authoritative. V18 may extend existing WhatsApp routes but must not introduce a second response envelope.

### 3.7 Database boundary

**Locked:** existing `WhatsAppConversation` / `WhatsAppMessage` schema remains the baseline. Any future schema change requires an explicit migration and must be additive/backward-compatible where possible.

## 5. Explicit Non-Gaps

The following are **not** V18 rewrite targets because they already satisfy the architectural boundary:

- WhatsApp provider abstraction.
- Conversation persistence model.
- Message persistence model.
- Channel-aware conversation uniqueness.
- `externalMessageId` uniqueness.
- Existing BusinessLead relation.
- Existing admin authentication boundary.
- Existing `/admin/whatsapp` route.
- Existing customer context projection.
- Existing audit infrastructure integration.
- Existing Graph API outbound client.
- Existing provider error mapping.

## 6. Architecture Decisions Locked by V18.0

1. Do not rebuild WhatsApp from scratch.
2. Preserve the V17 WhatsApp implementation and evolve it additively.
3. Meta Cloud API remains the provider boundary.
4. ReadyScore owns conversation data and operational inbox experience.
5. `BusinessLead` remains the existing identity/context system.
6. No duplicate customer identity system.
7. Existing auth/RBAC remains authoritative.
8. Existing API response contract remains authoritative.
9. No automatic data deletion.
10. No production mutation during V18.0.
11. Question Architecture V17.11 remains frozen.
12. V18.1 owns core runtime gaps.
13. V18.2 owns admin operational completion.
14. V18.3 owns hardening, regression, local certification, and production certification.

## 7. Implementation Boundary

### V18.0

Architecture and baseline only. No runtime feature rewrite.

### V18.1

Implement only the runtime gaps identified in this matrix, especially webhook processing safety, inbound normalization, outbound/status certification, idempotency, and provider error behavior.

### V18.2

Complete and certify the operational admin inbox and customer context.

### V18.3

Harden security/performance, run full regression, run local WhatsApp E2E, and only then prepare production certification.

## 8. V18.0 Acceptance

V18.0 is considered architecturally complete when:

- the existing WhatsApp implementation is mapped;
- every material gap has an owner phase;
- no unnecessary rewrite remains implied;
- API, security, database, identity, and provider boundaries are explicit;
- Question Architecture remains frozen;
- no production mutation is performed.

**V18.0 architecture baseline: PASS** is only asserted after the static gate supplied with this baseline is run successfully.
